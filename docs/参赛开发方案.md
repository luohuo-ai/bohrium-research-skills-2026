## 当前规则及其影响

第一期赛事页写明十题分别评分，奖励按十题累计得分判定。题面均采用五个评分维度：实际效果 40、使用增益 25、创新增益 15、可靠体验 10、生态贡献 10。

每题提交的是 `SKILL.md` 和实际需要的文本资源。平台把 Skill 装入 `/skills/weekly-skill`，通过官方 DeepSeek Harness 在三个固定原始案例上运行；每个条件重复三次。正式案例、对照白板和正式结果由平台提供或生成，不能把本地示例包装成这些正式结果。

单次案例的题面预算为 64 次模型请求、900 秒、每个响应含推理最多 16384 tokens。Skill 包最多 50 个 UTF-8 文本文件，每个不超过 500 KB、总量不超过 2 MB，不允许符号链接。运行生成的 PDF、Office 文件等二进制产物另行保留。

读取 `/input/case.json`、实际 `task.md` 和资源声明，保留原始 `output_contract` 要求的全部字段与 `case_id`。工作文件写到 `/app/work`，结果与可编辑产物写到 `/app/output`。涉及可视化或 Office 产物时，必须提供真实渲染预览；材料不足时应保存明确标注边界的部分结果。

五道阅读题当前题面明确提供有效 GitHub 公开作品链接最高额外 5 分，并要求根目录有 `GITHUB_URL.txt`；五道写作题的当前题面没有这一附加项。附加分怎样进入校园总榜没有另行明确，不能直接把潜在总分上限认定为 1025。发布公开仓库须在作品完成、内容可审阅后另行取得用户明确授权。

### 必须处理的评测不一致

当前文献文档解析题接口声明 `llm_judge_topic_markdown`，其余九题声明 `human_review_only`；它们的正文却均描述固定案例和 DeepSeek Harness 运行。解析题接口另列出 ARM 通用产物，而正文要求只交 Skill。正式案例运行环境的完整 `environment/resources.yaml` 也没有随当前 CLI 下载出现。

这些差异不阻止阅读、设计、开发和本地预检，但会影响正式评测能否启动以及分数能否及时反馈。正式提交前重新查询当前规则与 CLI 预检结果；若仍不能确定评测入口、提交开放期或校园榜关联方式，则把具体差异整理给用户，请用户向组织方确认。未经用户明确指示，不代发群消息或讨论帖。

API 的 `roundId`、`roundEndAt` 当前为空，不能用这两个空值代替赛事页的校园截止安排。按赛事页和手册记载，第一期截止为北京时间 11 月 29 日 24:00；提交前重新核对当期正式公告。

## 开发方式的选择

方案一是十题完全分开开发。每题可独立调整，但会重复实现证据定位、结果结构、数值保护与资源探测，测试成本较高。

方案二是复用小型公共组件，各题保留独立的 Skill 入口和专项流程。公共组件解决来源定位、输入输出契约、运行记录和确定性检查，各题只携带实际需要的组件。它有利于在本期覆盖十题，但必须防止把十题变成同一份泛化提示。

采用方案二，这是本次建议的实现选择，尚待用户确认。首批开发学术润色与结构化笔记，用这两个任务验证公共组件和打包路径，再扩展到其他题目。

## 公共组件

1. **输入与能力发现**：先读真实输入、任务约束和资源清单；记录实际存在的工具和版本。可选 PDF/OCR/TeX/Office 工具按可用性选择，不假设个人电脑路径或某个解析库在平台中必然存在，不把缺软件写成运行成功。
2. **来源与证据记录**：记录来源文件标识及内容哈希、页码或原生段落定位、原文片段、所支持的结论或字段。相同文件哈希或片段哈希可用于标识稳定性，不能代替人工可读的位置；没有页码时按材料实际结构定位。
3. **字段与事实保护**：保护数字、单位、公式、引用标记和限定条件。脚本检查可确定的问题；语义关系和指代仍需 Agent 对照原文审查，不能把字符检查通过等同于语义正确。
4. **覆盖与冲突检查**：根据本案要求建立覆盖清单，区分未报告、冲突、缺文件、执行失败和无法判断。保留冲突双方的来源，不擅自选取能让结果更好看的数值。
5. **结果与运行记录**：尽早保存可用中间结果，最终按本案原始契约写 `result.json` 和所需真实产物。记录实际调用、工具版本、失败及修复；不记录或输出任何凭据。自定义公共字段不得覆盖本案要求的字段。

各提交目录自包含：必要共享脚本会复制到各题目录中，以相对路径引用，不用符号链接，也不依赖其他题的目录、作者个人文件、全局 Codex Skills 或联网读取本仓库。

## 开发和验证的边界

本地使用公开许可材料或自行构造的小样本，明确标为开发样例；正式三个案例和白板不在手，不能报告其成绩。每题建立能暴露真实失败模式的测试，不仅检查文本中有没有某些标题。

先验证确定性组件：文件与字段覆盖、证据回链、数字引用保护、去重、编号、结构化序列化和失败路径。再通过实际 Agent 调用检查工作流。平台的固定模型、预算和对照若本地不可获得，则不声称本地检验等同于正式评测，也不编造“相对基线提升百分比”。

本机已检测到 pypdf、pdfplumber、Pillow、python-docx、lxml 和 ReportLab；PyMuPDF、rdflib、jsonschema 及 OCR/TeX 编译器目前未在所检查的 Python 环境或 PATH 中检测到。该结果不代表平台镜像的能力，也不代表本机所有工具目录都没有相关程序。首批尽量使用现有资源；确需新增运行依赖时选择 D 盘内隔离安装。现有安装可继续使用，不能把静态检查标为真正 OCR 或 TeX 编译成功。

正式 Skill 中的工具发现、容错和超时安排必须适应 900 秒总预算。无需读取的参考文件不一次性加载，保留最终检查及保存产物所需余量；遇到耗时失败时保留已完成部分，避免耗尽预算后没有可用交付。

## 预检和提交

每题开发完成后检查 YAML、相对路径、全部文本编码、文件数与体积、必要资源和适用边界；运行官方 `submit --dry-run`。明确指定当前真实会话日志，不使用自动选择到的其他聊天日志。

原生日志格式验证已通过，CLI 源码也包含 API Token 的脱敏逻辑；这还不能替代最终打包检查。实际打包后检查生成的材料与日志没有完整令牌、密码、凭据文件、其他项目材料或未授权公开的内容。保留真实事件，不手写或伪造开发轨迹。

每道题正式评测应有提交原因和版本记录。官方文档写明每题最多十次计分提交，未形成分数的失败另算；因此以本地测试和 dry-run 排除可发现问题，再按实际反馈改进，不能用十次额度代替基础检查。排队、运行中、临时分、人工评审和最终分分别记录；只有最终可用于榜单的分数才计入已确认成绩。

GitHub 加分作品先在本地整理并检查许可证、文件和敏感内容。没有获得发布授权或没有可验证的公开链接时，不创建假链接，也不声称得到附加分。
